# 「已适配 / 未适配」判断方法

应用列表的状态不再读取本机图标包目录，而是以用户导入的**模块 zip** 为准：
zip 里有该包名 → 已适配，没有 → 未适配。这样判断的就是「模块会不会在暗色下换掉这个图标」，
不受本机是否刷入模块、系统目录是否同步的影响。

| 状态 | 含义 | 暗色模式下的表现 |
| --- | --- | --- |
| 已适配（`MODULE`） | 导入的模块 zip 里有该包名的图标目录 | 桌面使用模块里的暗色素材 |
| 未适配（`NONE`） | 模块 zip 里没有该包名 | 仍是原来的图标 |

> 判断只看「模块 zip 里有没有」，不再区分 APK 自身是否带夜间图标。

---

## 1. 使用流程

```
左侧抽屉 →「模块图标包」→「导入模块 zip」
            │
            ▼
   解析 zip，得到包名集合（并保存到本地）
            │
            ▼
   扫描桌面入口（ACTION_MAIN + CATEGORY_LAUNCHER）
            │
            ▼
   包名在集合里？── 是 → 已适配（MODULE）
            └────── 否 → 未适配（NONE）
```

导入完成后会自动重新扫描；下次启动直接复用上次解析的包名集合，
抽屉里显示文件名与应用数量，可随时重新导入或清除。

## 2. zip 里如何识别包名

兼容三种常见布局：

| zip 内的路径 | 说明 |
| --- | --- |
| `my_product/media/theme/uxicons/hdpi/<包名>/...` | 模块 zip 直接展开的图标目录 |
| `<包名>/...` | 模块里内嵌的 `icons.zip` |
| `uxicons/<包名>/...` | 模块里内嵌的 `uxicons.zip` |

内嵌的 zip 用流式方式继续读取，不会整包读进内存，几百 MB 的模块包也不会 OOM。

目录名的处理规则：

| 目录名 | 处理方式 |
| --- | --- |
| `com.example.app` | 直接对应包名 |
| `com.example.app.ui.MainActivity` | 应用列表比对时按 `包名.` 前缀命中 |
| `com.a.one和com.b.two` | 按「和」拆成两个包名 |
| `plus.H5925EFE7` | 主题商店哈希 ID，无法映射，跳过 |
| `temp_*` / `.*` / `*.bak` | 临时、隐藏、备份目录，跳过 |

## 3. 已知局限

- **只判断模块覆盖范围**：zip 里有目录即视为已适配，不检查素材是否真的生效
  （例如 `rec_night.png` 只是 `recfg.png` 的副本）；需要肉眼确认时可以导出图标对比。
- **不区分应用自带的夜间图标**：APK 自己实现了暗色图标的，只要模块没覆盖，
  列表里仍然显示未适配。
- **前缀命中可能误判**：`com.foo` 会命中 `com.foo.bar` 这类目录，
  与 ColorOS 按包名前缀匹配入口图标的规则一致，属于可接受的近似。
- **扫描范围**是桌面入口应用。没有 `CATEGORY_LAUNCHER` 的应用不会出现在列表里。
- 模块 zip 是**全量素材**，而列表只统计本机已安装的应用，
  所以「已适配 115 个」和模块里几千个目录本来就不一致。

## 4. 如何验证

1. 导入模块 zip，在筛选里选「已适配」，确认目标应用在列表里；
2. 手机切到深色模式，看桌面目标应用图标是否变化；
3. 想看资源层的原始差异：勾选该应用导出，zip 里 `icon.png` 是日间整图，
   已适配的应用还会有 `icon2.png`（APK 夜间整图）。

若判断与预期不一致，先检查模块 zip 里是否真的存在该包名目录
（可以是 `hdpi/<包名>/`、`<包名>/` 或 `uxicons/<包名>/` 三种形式之一）。
