# 「已适配 / 自适配 / 未适配」判断方法

应用列表里的状态标签由 `IconExtractor.detect()` 计算，结果是一个三值枚举
`AdaptState`（[AppItem.kt](../code/app/src/main/java/io/github/imroxy2222/coloros17perfecticon/icon/AppItem.kt)）。

| 状态 | 含义 | 暗色模式下的表现 |
| --- | --- | --- |
| 已适配（`MODULE`） | 模块图标包里有该应用，且 `rec_night.png` 与 `recfg.png` 内容不同 | 桌面显示包里的暗色前景 |
| 自适配（`SELF`） | 图标包没有该应用，但 APK 自身在夜间会渲染出不同图标 | 桌面跟随应用自带的夜间图标 |
| 未适配（`NONE`） | 上面两种情况都不满足 | 仍是日间图标 |

> 「未适配」只说明**当前没有可用的暗色图标**，不代表应用本身有问题。

---

## 1. 判定顺序

```
读取桌面入口（ACTION_MAIN + CATEGORY_LAUNCHER）
            │
            ▼
  图标包里有该包名？
   ├── 是 ──→ rec_night.png 与 recfg.png 内容不同？
   │           ├── 是 → 已适配（MODULE）
   │           └── 否 → 未适配（NONE）※ 包覆盖了图标，APK 夜间资源不会生效
   │
   └── 否 ──→ APK 在日/夜配置下渲染结果差异 ≥ 2%？
               ├── 是 → 自适配（SELF）
               └── 否 → 未适配（NONE）
```

图标包优先的原因：ColorOS 桌面只要在 uxicons 里找到目录，就用包里的
`recbg + recfg/rec_night` 重绘，完全忽略 APK 自己的 `-night` 资源。所以
「包里有目录但夜间前景和日间一样」必须算未适配，不能因为 APK 带夜间图就算自适配。

## 2. 图标包查询（已适配 / 未适配）

读取下面两个根目录，任意一个命中即视为「包里有该应用」：

| 路径 | 说明 |
| --- | --- |
| `/my_product/media/theme/uxicons/<density>/` | 模块源目录（随模块刷入） |
| `/data/oplus/uxicons/` | 安装后系统实际使用的目录 |

`<density>` 形如 `hdpi` / `xxhdpi`，目录不存在时直接跳过。

目录名与包名的对应规则：

| 目录名 | 处理方式 |
| --- | --- |
| `com.example.app` | 直接对应包名 |
| `com.example.app.ui.MainActivity` | 以 `包名.` 开头的目录，视为该应用的入口图标 |
| `com.a.one和com.b.two` | 拆成两个包名，分别命中 |
| `plus.H5925EFE7` | 主题商店哈希 ID，无法映射，跳过 |
| `temp_*` / `.*` / `*.bak` | 临时、隐藏、备份目录，跳过 |

「已适配」还需要满足（满足其一即可）：

- 目录里存在 `rec_night.png`，且有 `recfg.png` 时两个文件**字节不相同**（`contentEquals`）；
- 目录里存在 `nsd.png`（暗影整图：近黑底板 + 彩色图形），且有 `recfg.png` 时两者内容不同。

只把 `recfg.png` 复制一份改名成 `rec_night.png`、又没有 `nsd.png` 的素材，夜间仍是
白天那张图，判定为未适配（例如贴吧 Lite）；而滴滴出行这类 `rec_night` 是副本、
但带 `nsd.png` 的应用，会按暗色素材判定为已适配。

## 3. APK 夜间图标比对（自适配）

仅对「包里没有」的应用执行，步骤：

1. 用 `PackageManager` 取桌面入口的 `iconRes`；
2. 分别构造 `UI_MODE_NIGHT_NO` 与 `UI_MODE_NIGHT_YES` 的 `Configuration`，
   把 `densityDpi` 提到 640 后 `createConfigurationContext`，各取一次 Drawable；
3. 两者都按自适应图标的 1.5 倍可视区域渲染成 160×160 的 ARGB_8888 位图；
4. 逐像素比较，忽略轻微差异：
   - 只有 RGB 各通道差值与 alpha 差值的总和 > 32 才记为「变化像素」；
   - 变化像素占比 ≥ **2%** 判定为自适配，否则视为没有夜间图标。

阈值的目的：抗锯齿、解码误差这类一两个像素的抖动不会被当成夜间图标；
而真正换了一套暗色资源（底色反转、前景改白色）通常有 70% 以上的像素不同。

## 4. 已知局限

- **只认资源层的差异**。应用如果在设置里切换主题、图标本身是静态图片，
  资源层没有任何痕迹，无法检测。
- **动画图标**（部分应用图标带 AnimatedVectorDrawable 或随机图案）两次渲染
  本身就可能不同，存在被误判为自适配的可能。
- **包覆盖优先于 APK**。见第 1 节：只要图标包里有目录，就不再看 APK 的夜间资源。
- **扫描范围**是桌面入口应用。没有 `CATEGORY_LAUNCHER` 的应用不会出现在列表里。
- 模块打包进 zip 的是**全量素材**，而列表只统计本机已安装的应用，
  所以「已适配 92 个」和应用里看到的数量本来就不一致。

## 5. 如何验证

1. 手机切到深色模式，看桌面目标应用图标是否变化；
2. 列表里每个应用并排显示两个预览：标「亮」的是日间渲染结果，标「暗」的是
   APK 夜间模式下的渲染结果，两者不同说明应用自身带暗色图标；
3. 在本应用里把该包名加入筛选，确认状态标签与桌面表现是否一致；
4. 想看资源层的原始差异：勾选该应用导出，zip 里 `icon.png` 是日间整图，
   `icon2.png` 是 APK 夜间整图（仅自适配/已适配应用才有），对比两张图即可。

若发现判断与桌面表现不一致，优先检查该包名是否已存在于
`/my_product/media/theme/uxicons/hdpi/<包名>/` 或 `/data/oplus/uxicons/<包名>/`，
以及目录里的 `rec_night.png` 是否只是 `recfg.png` 的副本。
